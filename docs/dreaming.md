# 夜间记忆整理（dreaming）

> **何时读**：改 `bin/memlint.py`、改「记忆整理（夜间 dreaming）」这个定时任务、或解释某一夜为什么改了某条记忆时（读）

## 为什么是「整理」而不是「积累」

本设施的长期记忆在磁盘上：`journal/`（经过）、`reports/`（判断与报告）、
`.future/memory/` + `FUTURE.md`（下一位要读的结论）。记忆失效的方式不是「不够多」，而是
**堆叠**：

- 顶到上限后被加载器静默截断，谁也不知道丢了哪条；
- 旧结论没被标掉，新结论只是追加在后面，读者先读到的是过期那版；
- 条目失去日期后，「过期要复核」这条规则再也命中不了它；
- 断言停留在写下那天的现实，而现实变了——这种错**读文本永远发现不了**，因为文本自身不自相矛盾。

具体到本机的实测基线（体积、陈旧比例、追加式更正的文件数）记在
`.future/memory/dreaming-baseline.md`，不进 git；那份文件同时是「本轮该修到什么程度」的对照。

## 五条规则

1. **年龄不删条目。** 7 天只代表「依赖前复核」。删除只由**被证伪**或**被取代**触发。
   稳态事实（工具链路径、目录约定、用户偏好）几个月不变，过期只需重跑一条验证命令刷新日期。
2. **容量走归档。** 顶到上限时，把条目移到 `.future/memory/archive/<日期>/`，`FUTURE.md`
   留一行指针；**不做删除**，也不让加载器随机截断。
3. **单源。** `memory` 只放「指针 + 一句话结论 + 日期 + 怎么验」；细节留在所属仓的 docs。
   同一事实不许两处各写一份——复制必然分叉。
4. **取代必留痕。** 更正写成 `~~旧说法~~ → 新说法（日期）` 或 `SUPERSEDED(日期) by …`，
   让读者一眼分辨哪句是现行的。
5. **可机检的才算事实。** 凡写命令、路径、端口、周期、ID 的，应附一条能跑的验证；
   跑不了的标 `unverified-since <日期>` 并留会话 id 供追溯。

## 两个阶段，成本递增

- **阶段 1 · 机械检查（零模型）**：`python3 bin/memlint.py`
  （`--record` 写入台账，`--json` 机器可读，`--workspace` 指定工作区，`--selftest` 自检）。
  检查项：容量、未带日期的条目与文件、死链、重复标题/重复目标、**未标取代的追加式更正**、
  以及文中引号路径的存在性。**memory 文件是不受信输入**：脚本只按路径存在性核对，
  **从不执行 memory 里写的任何命令**。报告写到 `reports/memory/<run_id>.md` 与 `latest.md`。
  「未标取代」这一项只认**动作**不认词：同一行里既要有替换类动词（不再/改为/更正/作废…）
  又要明确指向被替换的那句（此前/原先/旧说法/之前写的是…），且本文件没有用 `~~` 或
  `SUPERSEDED(…)`；光是正文里出现「不再」「修正」不算——那描述的是世界，不是本文件里
  被作废的说法（只按词匹配会把每个用过这些词的文件都报一遍，而它们多半什么也没作废）。
  两个方向都由 `bin/memlint.py --selftest` 钉住，`bin/selfcheck.py` 会实际跑它。
- **阶段 2 · 语义整理（模型，只处理阶段 1 报出的条目）**：同一话题两份文件互相否定、
  索引行与话题文件不一致 → 合并/标取代；**只在本仓 `.future/memory/` 与 `FUTURE.md`
  上直接改**，别仓的 `FUTURE.md` 进 git，只能出 PR 提案。

## 谁能改什么

| 范围 | 允许 |
|---|---|
| 本仓 `.future/memory/`、`FUTURE.md`（本地，不进 git） | 直接改，且只限三类：刷新日期、标取代、补验证命令；超限则归档 |
| 其他仓的 `FUTURE.md` / docs | **不自己代笔**：派一个以该仓为工作区的新会话去改（见下节） |
| `journal/`、`reports/`、`state/` | 只追加，不改写历史 |
| `.private/`、任何凭据文件 | 不读、不写、不引用 |

## 别仓的整理：派一个新会话，而不是代笔

同一个事实，在自家记忆里改和在别人的仓里改不是一回事：那个仓有自己的 `AGENTS.md`、目录约定、
测试命令与评审流程，而**只有以它为工作区启动的会话才读得到这些**。所以本任务对别仓只做两件事：
发现，和派工。派工用 `bin/send.py --new --cwd <那个工作区> --accept <完成判据> <brief>`，
brief 里写全背景、逐条 `文件:行` 的发现、可做的四类改动、边界与验收（模板见
`prompts/dreaming.md` 第 3 节）。同一个工作区一天最多派一次。

## 留痕与审计

每一夜三份记录，都能事后追：

- `reports/memory/<run_id>.md` — 人读的发现清单 + 「这一轮做了什么」；同一次运行（`--run-id`
  相同）的重复扫描追加成「再一次扫描」，**一轮一份文件**，不给同一夜留一堆碎片；
- `reports/memory/latest.md` — 永远是最新一次扫描；
- `state/memlint.jsonl` — 机械检查台账（一行一次运行：工作区、按类型计数、全部 finding）；
- `state/dreaming.jsonl` — 整理动作台账（一行一次运行：改了哪几条、跳过哪几条、派给谁、待确认哪几条）。

改一条记忆要能回答三个问题：**依据是什么**（哪次运行/哪个会话）、**怎么验的**（跑过的命令）、
**怎么退**（旧说法在 `~~` 或归档里）。答不上来的改动就不该做。

## 验收（可证伪）

- 索引体积回到上限内且条目数不越界（或已有归档指针）；
- 无日期条目/文件、未标取代的追加式更正**剩余数**逐周下降——看「还剩多少」，不看「本轮报了多少」；
- **断言回验发现的真错数**：第一周 ≥1 条说明这活有料；连续两周 0 条且不再超限 → 降频到每周，
  别为了跑而跑；
- 每天实际改动应 ≤5 条；更多说明规则太松。
